# Analysis

!!! info "What you need to know"

    You must be able to identify the:

    * purpose

    * scope

    * boundaries

    * functional requirements
    
    of a problem that relates to the design and implementation at this level, in terms of:

    * inputs

    * processes
    
    * outputs

## Purpose

The __Purpose__ is a really important part of the analysis stage. It’s all about clearly stating what the software is meant to do – basically, what problem it’s solving or what task it needs to complete. 

A clear purpose helps everyone involved understand what the end goal is, and it makes sure the rest of the project stays on track. 

In addition, it also helps when you’re thinking about what the program will need to take in (__inputs__), what it will do (__processes__), and what it should produce (__outputs__). 

If the purpose isn’t clear, it’s easy for the software to end up doing the wrong thing or not meeting the user’s needs. A good purpose is simple, focused, and makes it easy to check if the final product works the way it’s supposed to.

The SQA define purpose as a __general description__ of the software. At Higher, this should explain what the system is designed to achieve rather than listing every feature in detail.

This is often summarised using the **IPO model**:

- **Inputs** – What information the program receives  
- **Processes** – What the program does with that information  
- **Outputs** – What the program produces or displays  

This model helps developers stay focused on what the software is meant to do, and it links closely to the functional requirements.

### Purpose Example

**Problem:** A school library wants a system to manage book loans.

**Purpose:**
To allow library staff to record when books are borrowed and returned, and to display information about current loans.

Notice that the purpose gives a general overview of the system rather than a detailed list of every feature.

## Scope

The __Scope__ is where you set the boundaries of what the software will and won’t do. 

Once the purpose is clear, the scope builds on that by outlining exactly what features or tasks will be included in the project – and just as importantly, what’s being left out. 

This helps keep the project realistic and manageable, especially if there are time or resource limits. It also stops feature creep, where new ideas get added in along the way and make everything more complicated. 

A clear scope gives everyone – from developers to users – a shared understanding of what to expect, which makes planning and development much smoother.

### Scope Example

For the school library system:

**Included in the scope:**
- Record book loans
- Record returned books
- Search for books
- Display current loans

**Not included in the scope:**
- Online book reservations
- Automatic email reminders
- Stock ordering from suppliers

This helps developers understand exactly what features should be developed within the project.

!!! note "Exam Tip"

    In a Higher exam question, you would not normally be expected to write separate **Included** and **Not Included** lists.

    These have been used here as a teaching strategy to help you visualise the scope of a system and understand where the limits of the project lie.

    In an exam, scope is often described in a short paragraph that explains what the system will do.

## Boundaries

The __Boundaries__ identify what’s outside the system – in other words, the parts the software won’t deal with. While the scope tells us what’s included in the system, boundaries help make it clear where the system ends and where other systems or people take over. 

For example, if a program needs information from a database but doesn’t manage the database itself, that database would be outside the boundary. 

Setting boundaries is useful because it helps avoid confusion about what the software is responsible for. It also makes it easier to plan and design the system by focusing only on what actually needs to be built.

### Boundary Example

For the school library system:

- The system records loans and returns.
- The librarian is responsible for physically issuing books.
- The school's email system is responsible for sending any notifications.
- The school's network infrastructure is managed by IT staff.

These external people and systems sit outside the boundary of the software being developed.

## Scope vs Boundaries

Many pupils confuse **scope** and **boundaries** because both describe limits. However, they focus on different things.

| Scope | Boundaries |
|---------|---------|
| Describes what features and functions the software will and will not provide. | Describes what people, systems or responsibilities exist outside the software. |
| Focuses on functionality. | Focuses on responsibility. |
| The system will not send email notifications. | The school's email system is responsible for sending notifications. |
| The system will not manage room bookings. | School staff are responsible for allocating rooms. |

A useful way to remember the difference is:

- **Scope = What the software does**
- **Boundaries = Who or what is outside the software**

## Worked Example: School Club Registration System

A school wants a simple system that allows pupils to register for after-school clubs.

### Purpose
To allow pupils to view available clubs and register for a club. Teachers can view a list of pupils who have signed up.

### Scope
**Included:**
- Display available clubs
- Register a pupil for a club
- View attendee lists

**Not Included:**
- User accounts and login systems
- Email or text notifications
- Room booking management

### Boundaries
- Teachers are responsible for creating clubs.
- Pupils are responsible for entering their own details correctly.
- Any school email system operates outside the software.
- The system does not manage staffing or room allocations.

### Why this is a good Higher answer

- The **purpose** provides a general description of the system.
- The **scope** identifies what features are included and excluded from the system.
- The **boundaries** identify responsibilities that sit outside the software.
- The **functional requirements** are clearly linked to inputs, processes and outputs (IPO).
