# Data Flow In and Out

!!! info "What You Need to Know"

    You must be able to identify the data that flows **into** and **out of** modules in a design.

## Purpose

**Data flow** shows the information passed between modules in a program design.

At Higher, it is not enough to show that a program has modules. You also need to show what data each module needs and what data it produces.

This helps another programmer understand:

- which modules depend on each other
- what variables or arrays are passed between modules
- what parameters may be needed when the program is implemented

## The Main Rule

Only show data flow when data moves **between modules**.

Do not list external sources or destinations as data flow.

| Do not show | Show instead |
|---|---|
| Keyboard | The variable that stores the input |
| File | The variables or arrays read from the file |
| Screen | The variables needed to produce the output |
| Printed report | The variables needed to create the report |

For example, a module may read pupil marks from a file. The file is not shown as data flow. The arrays created from the file are shown as data flow because they are passed to other modules.

```text
1 Get results
  OUT: pupilName(), prelimMark(), courseMark()
```

The module produces `pupilName()`, `prelimMark()`, and `courseMark()` for later modules to use.

## IN, OUT, and IN/OUT

Data flow is usually labelled using `IN`, `OUT`, or `IN/OUT`.

| Direction | Meaning | Example |
|---|---|---|
| `IN` | Data passed into a module | `marks()` |
| `OUT` | Data produced by a module and passed out | `average` |
| `IN/OUT` | Data passed in, changed, and passed back out | `total` |

Use these questions to decide the direction:

- Does the module need this data before it can work? Use `IN`.
- Does the module create this data for another module to use? Use `OUT`.
- Does the module receive the data, change it, and pass it back? Use `IN/OUT`.

## Worked Example

The top-level design below has three modules.

```text
1 Get scores
2 Calculate average
3 Display average
```

To add data flow, think about what each module needs and produces.

### 1 Get scores

This module gets the scores from the user or from a file.

The keyboard or file is not shown as data flow because it is outside the module design.

```text
1 Get scores
  OUT: score()
```

The module produces the `score()` array.

### 2 Calculate average

This module needs the scores before it can calculate the average.

```text
2 Calculate average
  IN: score()
  OUT: average
```

The module receives `score()` and produces `average`.

### 3 Display average

This module needs the average so it can display it.

```text
3 Display average
  IN: average
```

The screen is not shown as data flow. The module uses `average` to produce the screen output, but it does not pass new data to another module.

The complete data flow design is:

```text
1 Get scores
  OUT: score()

2 Calculate average
  IN: score()
  OUT: average

3 Display average
  IN: average
```

## What Counts as Data Flow?

Ask this question:

> Is this data being passed from one module to another module?

If the answer is yes, it is data flow. If the answer is no, it is probably an external input, external output, or data used only inside one module.

| Action | Is it data flow? | Why? |
|---|---|---|
| User types a mark | No | The data comes from outside the program design |
| A module reads names from a file | No | The file is external to the module structure |
| A module passes `names()` to another module | Yes | Data moves between modules |
| A module calculates `average` for another module to display | Yes | The calculated value is passed to another module |
| A module displays a result on screen | No | The result is sent outside the module design |
| A module uses a counter inside a loop | No | The counter is only used inside that module |

!!! warning "Common mistake"

    Do not list the keyboard, screen, or a file as data flow. Show the variables or arrays that move between modules.

A data flow table should list the module names and the data that moves in or out of each one.

For example:

| Module | IN | OUT |
|---|---|---|
| Get song data |  | `songName()`, `artistName()`, `downloads()` |
| Find most-downloaded song | `downloads()` | `topPosition` |
| Display most-downloaded song | `songName()`, `artistName()`, `downloads()`, `topPosition` |  |

## Data Flow in Pseudocode

The same data flow can be shown beside the steps in pseudocode.

```text
1 Get song data
  OUT: songName(), artistName(), downloads()

2 Find most-downloaded song
  IN: downloads()
  OUT: topPosition

3 Display most-downloaded song
  IN: songName(), artistName(), downloads(), topPosition
```

The brackets in names such as `songName()` and `downloads()` show that they are arrays.

## Link to Parameters

Data flow helps you decide the parameters for procedures and functions.

```text
Find position of pupil with top mark
IN: percentage()
OUT: topPosition
```

This could become a function that receives `percentage` as a parameter and returns `topPosition`.

## Checklist

A good data flow design should:

- use meaningful data names
- show arrays clearly, often using brackets such as `marks()`
- show whether data is `IN`, `OUT`, or `IN/OUT`
- avoid listing files, screens, keyboards, or reports as data flow
- match the modules in the structure diagram or pseudocode
- make the parameters for implementation clear

## Summary

Data flow shows the information passed between modules in a design.

The main rule is that data flow only shows data moving from one module to another. It should not show external sources or destinations such as the keyboard, screen, files, or printed reports.

A good Higher data flow design should show:

- what data each module needs
- what data each module produces
- which variables or arrays move between modules
- whether the data is `IN`, `OUT`, or `IN/OUT`
- how the data flow could become parameters in the final program

Data flow helps another programmer understand how information moves through the solution before the program is implemented.
